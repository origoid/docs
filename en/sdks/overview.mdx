We publish first-party SDKs for the three languages most used by OrigoID
customers. All three are auto-generated from the same OpenAPI specification,
so they always cover every endpoint and stay in sync with the API. There is
no community-maintained variant or alternative client to choose from —
these are the official, supported clients.

## Why use an SDK instead of raw HTTP

You can absolutely call our REST endpoints with `curl`, `fetch`, `requests`,
or `net/http`. The SDKs add:

- **Typed request and response models** — your IDE autocompletes every
  field, your compiler catches typos, your linter flags missing required
  values.
- **Embedded base URL** — `https://api.origoid.com` is baked in. There is
  nothing to configure in the client constructor beyond the API key.
- **Auth header handling** — pass your key once at construction time.
- **Automatic retries** — transient `5xx` and network errors are retried
  with exponential backoff (configurable per call).
- **Strongly-typed enums** — `type` codes, `cancellationStatus`, `riskLevel`,
  etc. surface as enums or string literal unions, never raw strings.
- **Helpful errors** — a `401 UNAUTHORIZED` throws an `UnauthorizedError`
  with the envelope already deserialized, not a generic `HTTPError`.

If you only need to call one endpoint occasionally from a script, `curl`
is fine. For any production integration we strongly recommend the SDK.

## Feature parity matrix

| Capability | Node | Python | Go |
| --- | :---: | :---: | :---: |
| All 19 endpoints | ✅ | ✅ | ✅ |
| Async (`await`) calls | ✅ native | ✅ via `AsyncOrigoID` | ✅ via `context.Context` |
| Sync calls | n/a (JS is async) | ✅ via `OrigoID` | ✅ (context can be `Background`) |

auto-generated by [Fern](https://buildwithfern.com) from
[`docs.origoid.com/openapi.json`](https://docs.origoid.com/openapi.json) on
every API release.

## Versioning

SDKs follow [semver](https://semver.org/).

- **Major** (`1.0.0` → `2.0.0`) — breaking changes to the SDK shape (rare;
  only when the underlying OpenAPI breaks). Always accompanied by a
  migration guide in the release notes.
- **Minor** (`0.1.0` → `0.2.0`) — new endpoints, new fields, new helpers.
  Backwards-compatible.
- **Patch** (`0.1.0` → `0.1.1`) — bug fixes, dependency updates, doc
  improvements.

While the SDKs are under `0.x.y` we follow the convention of bumping the
**minor** version for breaking changes (per semver pre-1.0 guidance) and
the patch version for everything else. Once an SDK reaches `1.0.0` the
classic semver rules apply.
