Some IMSS queries take longer than a client should wait on an open HTTP request, so they are offered as **asynchronous** endpoints. You send the request with a `webhook` object and we deliver the result to your URL when it is ready.

| Endpoint | Credits | Result |
|---|---|---|
| [Get NSS (Async)](/en/api-reference/social-security/get-nss-async) | 2 | Delivered to your webhook |
| [Employment Status (Async)](/en/api-reference/social-security/employment-status-async) | 2 | Delivered to your webhook |
| [Contribution Weeks](/en/api-reference/social-security/contribution-weeks) | 3 | Delivered to your webhook, with a 24-hour fallback |

## How it works

1. **Create the request.** `POST` the query together with a `webhook` object. The API answers right away with `type: ACCEPTED` and a `transactionId`. Accepting a request is free (`billable: false`).
2. **Receive the result.** When the query resolves, we send an HTTP `POST` to your `webhook.url`. The body is the standard [envelope](/en/envelope), with the **same `transactionId`** returned in step 1.

Request:

```json
{
  "curp": "RATL850312HDFMRS07",
  "webhook": {
    "url": "https://your-domain.com/hooks/origoid",
    "headers": {
      "Authorization": "Bearer YOUR_WEBHOOK_TOKEN"
    }
  }
}
```

Immediate response:

```json
{
  "status": "OK",
  "type": "ACCEPTED",
  "message": "Request accepted, result will be sent to the webhook",
  "data": null,
  "transactionId": "322e6c8b-0124-5c84-95db-4da04842d0da",
  "processedAt": "2026-03-15T19:23:30-06:00",
  "billable": false
}
```

If the request is not valid, you get `INVALID_REQUEST` right away instead of `ACCEPTED`, and it is never charged:

```json
{
  "status": "ERROR",
  "type": "INVALID_REQUEST",
  "message": "Validation failed",
  "data": null,
  "errors": [
    {
      "field": "curp",
      "code": "INVALID_FORMAT",
      "message": "curp is not a valid CURP"
    },
    {
      "field": "nss",
      "code": "INVALID_FORMAT",
      "message": "Invalid NSS format (must be 11 digits)"
    },
    {
      "field": "webhook",
      "code": "MISSING_REQUIRED_FIELD",
      "message": "must have required property 'webhook'"
    }
  ],
  "transactionId": "6117e20e-ea53-5424-87a9-da7576d4cd12",
  "processedAt": "2026-10-26T11:20:00-06:00",
  "billable": false
}
```

## The `webhook` object

| Field | Required | Description |
|---|---|---|
| `url` | Yes | Public `http` or `https` URL that receives the result. |
| `headers` | No | Header names and values we add to the webhook request — for example, your own token, so your endpoint can authenticate the call. |

## Your webhook endpoint

- It receives an HTTP `POST` with a JSON body (`Content-Type: application/json`) and the headers you configured.
- Answer with any `2xx` status as soon as you receive the body, and process it afterwards.
- Make it idempotent: the same result may be delivered more than once, so use `transactionId` to de-duplicate.

## Delivery attempts

We try to deliver each result up to **3 times**: right away, then 1 minute and 5 minutes after the previous failed attempt. An attempt fails when your endpoint does not answer with a `2xx` status within 10 seconds (redirects are not followed). After the third failed attempt the result is not sent again.

Keeping your webhook endpoint available is your responsibility: credits are charged when the result resolves, whether or not your endpoint receives it. For Contribution Weeks you can still fetch the result for 24 hours (see [Contribution Weeks fallback](#contribution-weeks-fallback)).

## Billing

Credits are charged once, when the result resolves, under the same rule as every other endpoint (see [Credits](/en/credits)): `billable: true` when the query was performed — even if the outcome is negative, such as `CURP_NOT_FOUND` — and `false` for technical failures. The `billable` field of the body your webhook receives tells you which applies.

### Contribution Weeks

How to read `data` (`SUCCESS` and `INACTIVE_EMPLOYMENT`):

- Official fields, taken from the IMSS document: `nss`, `personalInfo`, `contributionWeeks` (`total` = `contributed` − `discounted` + `reinstated`), `employmentHistory` (one row per job, newest first) and `reportDetails` (`folio`, `issueDate`, `digitalSeal`, …). `files[0]` is the official PDF in base64 (shortened in the examples).
- The active job is the `employmentHistory` row with `endDate: null`; in `INACTIVE_EMPLOYMENT` there is none.
- Everything computed lives in `derivedSignals` — `currentStatus`, `jobTenure` (months), `stability`, `salary` and `salaryTimeline`. They are facts, not a credit score.
- Salaries (`baseSalary`, `*Salary`) are the **daily** base contribution salary (SBC); the monthly equivalent is SBC × 30.44. `salaryAtLegalCap: true` means the salary hit the legal cap (25 UMA), so real income may be higher.
- Every field is always present; values that do not apply are `null`.

## Contribution Weeks fallback

If your webhook could not receive a Contribution Weeks result, fetch it for 24 hours with [Contribution Weeks Result](/en/api-reference/social-security/contribution-weeks-result) (free), sending the `transactionId`:

```json
{
  "transactionId": "975cf12f-f270-51cc-9037-d710134940c9"
}
```

It answers `RESULT_FOUND` (with the original result envelope inside `data`), `RESULT_PENDING` or `RESULT_EXPIRED`. Use it only as a fallback: the result is always sent to your webhook.
